# 功能規格書

## Metadata

- 功能：匯入學員個人資料 — Preview-then-Confirm（AF-021）
- 負責人：待補
- 狀態：草稿（設計決策已確認；待實作與驗證）
- 風險等級：高

## 問題

管理員需要以 CSV 或 Excel 批次建立學員個人資料，並在資料寫入前看見欄位錯誤與重複資料。匯入對象是 `User` 個人資料，不是課程報名、付款或 `Registrant` 記錄。

## 使用者

- 具 ADMIN 權限的管理員。

## 目標

- 接受 CSV / XLSX 學員範本檔，預覽解析結果與驗證錯誤。
- 只有整份檔案所有資料列有效時才允許確認。
- 確認時重新上傳並重新驗證檔案，再以單一資料庫交易建立全部使用者。
- `User` 是學員個人資料及身份證件欄位的唯一權威來源。
- 提供可下載的列/欄錯誤明細，協助管理員修正被拒絕的檔案。

## 非目標

- 不建立課程報名或付款資料。
- 不以此流程更新既有使用者；已存在的 email、身份證件號碼或 IA 牌照衝突視為驗證錯誤。
- 不保存上傳檔案或預覽資料於伺服器端暫存區、程序記憶體或資料庫。
- 不接受部分成功匯入。

## 使用者故事（User Stories）

| 故事 | 身為／我想要／以便 | 驗收標準 |
|---|---|---|
| 預覽學員檔案 | 管理員想在寫入前檢查資料，以便修正錯誤 | 預覽最多 20 列並顯示欄位與檔案結構錯誤；完整錯誤明細可下載；預覽不寫資料庫 |
| 原子式匯入 | 管理員想一次匯入完整有效檔案，以便避免不完整名冊 | 任一列無效或任何資料庫寫入失敗時，整份檔案均不寫入 |
| 下載範本 | 管理員想取得正確欄位範本，以便準備可解析檔案 | CSV 與 XLSX 範本使用同一組欄位標題 |

## 使用者旅程

```text
身為管理員
我想上傳、預覽並確認學員資料檔
以便只有完整有效的名冊會建立成 User 記錄
```

## 功能需求

- WHEN 上傳 CSV 或 XLSX THE SYSTEM SHALL 檢查副檔名與 10MB 大小上限。
- WHEN 檔案開頭含空白列 THE SYSTEM SHALL 跳過連續空白列，並要求第一個非空白列為範本標題列。
- WHEN 標題列包含範本所有欄名（不區分大小寫、欄位次序可變）THE SYSTEM SHALL 依標題對映欄位。
- WHEN 找不到完整標題列、標題列不完整或解析器無法解析檔案 THE SYSTEM SHALL 回傳可讀的結構錯誤，且不得建立可確認的預覽。
- WHEN 檔案有任何無效資料列 THE SYSTEM SHALL 顯示錯誤並停用確認；不得只匯入有效列。
- WHEN 管理員確認 THE SYSTEM SHALL 再次接收同一份檔案、重新解析及驗證，然後以單一 Prisma transaction 建立全部 User。
- WHEN 任一寫入失敗 THE SYSTEM SHALL 回滾整個交易並回報失敗；不得回報部分匯入成功。
- WHEN 匯入 ID 文件資料 THE SYSTEM SHALL 寫入 `User.idDocType` / `User.idDocNumber`；不得以 `Registrant` 上的同名欄位覆蓋或取代 User 值。
- WHEN email、身份證件號碼或 IA 牌照與現有資料或同一檔案中的其他列重複 THE SYSTEM SHALL 將整個檔案標記為無效。

## 畫面

| 畫面 | 狀態 | 備註 |
|---|---|---|
| `/admin/import/registrants` | 上傳、預覽、確認中、成功、檔案錯誤、列驗證錯誤、交易失敗、權限不足、行動裝置版 | 保留既有單頁三步驟版型；無效檔案不得確認 |

## 資料與 API

- 輸入：`POST /api/admin/import/registrants/preview` 與 `POST /api/admin/import/registrants/confirm` 均接受 `multipart/form-data` 的 `file` 欄位；confirm 重新上傳相同檔案，不使用 `importId`。
- 標題：依 AF-019 共用 parser 契約處理；使用範本的 8 個欄名，忽略前置空白列，第一個非空白列必須包含所有範本標題；標題比對不區分大小寫，允許欄位重新排序。
- 欄位對映：`nameZh`、`nameEn`、`email`、`phone`、`idDocNumber`、`idDocType`、`iaLicense`、`organization` 對應至 `User`；新使用者的 role 固定為 `STUDENT`。
- 輸出：preview 回傳列預覽、有效/錯誤筆數與結構錯誤；confirm 僅回傳整批成功或整批失敗結果。
- 驗證：必填欄位、email、電話、ID 類型、HKID 格式、資料庫既有重複及檔案內重複。
- 錯誤：結構錯誤或任何列錯誤均阻止確認；確認期間任一資料庫錯誤使交易回滾。
- 暫存：伺服器不保存檔案、解析列或預覽 session；confirm 請求重新上傳檔案並在交易前重驗。

## 安全性與隱私

- 身分驗證：所有端點要求有效 session。
- 權限：僅 ADMIN 可預覽、確認及下載範本。
- 敏感資料：檔案包含姓名、email、電話及身份證件資料；只在請求處理期間使用，不寫入暫存檔或伺服器 session。
- 濫用情境：伺服器重新檢查副檔名、大小及資料內容；不得信任 preview 回傳給瀏覽器的列內容；confirm 必須重新驗證。

## 驗收標準

1. CSV 與 XLSX 的開頭空白列會被略過，第一個非空白列須符合範本標題。
2. 標題缺漏或檔案格式不符時，顯示結構錯誤且無法確認。
3. 任一列無效時，整份檔案不可匯入；確認按鈕停用。
4. confirm 重新上傳、解析及驗證檔案，不依賴伺服器端 preview store 或 `importId`。
5. 所有列有效時，所有 User 在單一交易中建立；任一寫入失敗時資料庫沒有任何本批新增記錄。
6. `User` 是身份證件資料來源；匯入只建立 User，不建立 Registrant。
7. 資料庫既有重複與檔案內重複均會阻止整批匯入。
8. 範本下載提供 CSV 與 XLSX，副檔名及 10MB 上限檢查有效。
9. API 要求 ADMIN；preview 與 confirm 之間資料變更時，confirm 重新驗證並拒絕衝突。
10. Preview 提供 CSV 錯誤明細下載，包含原始列號、欄位及錯誤原因。
11. 所有新增/修改的 UI 文案使用 en、zh-hk、zh-cn dictionaries。
12. 整合測試證明交易失敗會完整回滾；`npm run typecheck` 與 `npm run lint` 通過。

## 驗證計畫

- 單元測試：AF-019 覆蓋標題列比對、前置空白列、錯誤標題與欄位重排；AF-021 覆蓋檔案內重複與 User 欄位 mapping。
- 整合測試：CSV / XLSX preview 與 confirm、ADMIN 權限、重複資料、全批回滾及 confirm 重驗。
- E2E：上傳範本 → 預覽 → 確認 → 驗證所有 User 建立；含無效列的檔案不寫入任何 User。
- 視覺：預覽列錯誤、結構錯誤、確認載入、成功與交易失敗狀態截圖。
- 手動：使用空白前置列與格式錯誤標題檔案驗證清楚錯誤訊息。
