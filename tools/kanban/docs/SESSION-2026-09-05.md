## Failures & Waste

### 1. S3 Storage Overhead (Removed)
- **Implemented**: PDF generated → S3 upload → presigned URL download + email via S3 fetch
- **Problem**: IAM user lacked `s3:GetObject` permission. "AccessDenied" errors.
- **Fix**: Removed S3 entirely. PDFs are generated on-the-fly from DB data every time.
- **Lesson**: If data is fully reproducible from the DB, don't introduce external storage. The S3 architecture was unnecessary complexity from the start. The card spec said "S3 upload" but nobody challenged *why*.

### 2. pdf-lib-encrypt Incompatibility (Removed)
- **Implemented**: `pdf-lib-encrypt` for AES-256 password protection on receipt PDFs
- **Problem**: "Offset is outside the bounds of the DataView" — `pdf-lib-encrypt` couldn't parse the output of `@react-pdf/renderer` v4's `renderToBuffer`
- **Fix**: Removed password protection entirely (accepted as "do later")
- **Lesson**: Never adopt a dependency without verifying it works with your specific library versions. Should have tested `pdf-lib-encrypt + renderToBuffer` in isolation before wiring it into the approval flow.

### 3. Font Registration Bug (Debugged)
- **Problem**: Both `fontWeight: 400` and `700` pointed to the **same Google Fonts URL** (the 400-weight woff2). The renderer received bold-weight glyphs from a normal-weight file, causing a buffer miscalculation and `DataView.setUint16` crash.
- **Detection**: Server stack trace showed crash *inside* `renderToBuffer`, not in `pdf-lib-encrypt`. This forced a wild goose chase blaming the encrypt module.
- **Fix**: Replaced Montserrat (Latin-only) with Noto Sans SC (CJK + Latin) using proper distinct URLs.
- **Lesson**: The bug was caused by a copy-paste error in the original code I wrote. If I had run the download immediately after PR-003, I would have caught this *before* adding S3 and encryption complexity.

### 4. Presigned URL → Proxy → On-the-Fly (3 Iterations)
- **v1**: Presigned GET URL via `getSignedUrl` → AccessDenied
- **v2**: Server proxy reads from S3 and streams → AccessDenied (same IAM issue)
- **v3**: Generate PDF on-the-fly from DB → works
- **Lesson**: I should have recognized the IAM constraint earlier and skipped directly to the DB-based approach. Three iterations to solve what should have been one.

### 5. renderToStream → renderToBuffer Migration
- Started with `renderToStream` + manual `streamToBuffer` helper
- `@react-pdf/renderer` v4 provides `renderToBuffer` directly (returns `Promise<Buffer>`)
- Switched to `renderToBuffer` — cleaner, fewer lines, no stream conversion
- **Lesson**: Always check the API docs for the version you installed before writing adapters.

### 6. Turbopack Module Collision
- Both `download/receipt/route.ts` and `generate.tsx` imported `pdf-lib` + called `configure()`
- Turbopack eagerly loaded both in the same module graph, causing double-configuration issues
- **Lesson**: Module-level side effects (`configure(PDFLib)`) are dangerous with Turbopack's bundling. Use dynamic imports for one-time setup, or ensure only one module calls `configure`.

## Root Cause Meta-Pattern

The session reveals a recurring problem: **adding complexity before validating the foundation**.

1. Wrote S3 upload without checking IAM permissions first → wasted time
2. Added pdf-lib-encrypt without testing it with the actual PDF render output → wasted time
3. Presigned URL → Proxy → On-the-fly: kept adding layers instead of stepping back

A better approach would have been:
1. Get a PDF to download with simplest possible code (just `renderToBuffer`)
2. Verify the PDF opens correctly
3. *Then* add S3, encryption, etc. one at a time
